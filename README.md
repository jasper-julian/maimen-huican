# 麦门会餐 · 饭局谈判官

多人一起吃麦当劳时，最低总价不一定是大家都接受的答案。这个作品把每个人的需求写成一张**匿名需求卡**，用真实门店菜单生成可比较的方案，展示**每个人拿到了什么、谁的要求没被照顾**，并且在有人说「这份我不接受」之后现场重谈一次，再用官方价格核对结果回答「多 10 元能换来什么」。

- 页面只出现用户能决定的业务信息，不出现接口名、schema 等开发术语。
- 只查询与试算：不下单、不支付、不领券、不兑换积分、不抽奖、不读收货地址。
- 官方场景固定「到店自取」；「堂食/外带」只是用餐说明，不冒充新的官方业务能力。

## 配置麦当劳官方 MCP

凭据只从这两处读取，绝不回显、不写日志、不进导出卡：

1. 环境变量 `MCD_MCP_TOKEN`；
2. 本项目 `.local/config.json` 的 `token` 字段（已 gitignore）。

页面右上角「连接设置」是本项目独立入口，会显示是否已检测到凭据及来源。已有有效配置时不需要重新填写，点「重新检查连接」即可。未配置时真实查询会明确失败；演示数据必须由用户主动点击，且全程标注「虚构」。

## 主流程

1. 填写城市与公开商圈（例如「上海 / 静安寺」），生成方案；未选门店时自动取该商圈第一家营业门店。
2. 1—4 张匿名需求卡（A/B/C/D），可在同一台设备依次填写想吃 / 不想吃。
3. 服务端查询该门店菜单与优惠，生成四种策略：
   - **优先满足口味**：先照顾想吃，再控制菜单估算；
   - **优先节省预算**：只保证每人一份可吃的主食；
   - **折中推荐**：主食 + 全桌最多一份共享加餐；
   - **照顾最难满足的人**：先抬高满足比例最低那位的比例，再比较其他人，最后才看价格。
4. 每张卡展示逐人分配、**满足/未满足清单**（计数 + 条目，不用满意度百分比）和菜单估算。
5. 任何人对分到的某项点「这份我不接受」→ 该人的明确排除项写入会话，服务端重新推荐并**重新做官方价格核对**；无解时展示具体冲突，不会自动放宽忌口或否决。
6. 「多 10 元能换来什么」→ 同一门店、同一策略、预算 +10 的相邻候选，两端都完成官方价格核对后才给出增量、新增/替换餐品、受益的人；否则如实说明没有变化或无法核对。
7. 选择一张方案卡后「导出所选方案卡」，得到不含口味原文、身份、Token、券码的脱敏 JSON。

## 真实验证（2026-10-24，上海 · 静安寺，只读）

门店「麦当劳上海静安寺餐厅」，87 个可用单品、3 个门店优惠；2 人（A 想吃鸡肉/不吃辣，B 想吃牛肉/不吃鱼），预算 ¥120：

| 策略 | 组合 | 官方实付 |
| --- | --- | --- |
| 优先满足口味 | 双层吉士汉堡 ×2、麦乐鸡、高达吉士双牛堡 | ¥86.00 |
| 优先节省预算 | 枫糖风味厚松饼猪柳堡、龙焰鸡腿堡 | ¥33.90 |
| 折中推荐 | 板烧鸡腿堡、双层吉士汉堡、麦乐鸡 | ¥60.00 |
| 照顾最难满足的人 | 与口味方案相同组合 | ¥86.00 |

四套方案均完成官方试算并通过商品编码/数量核对。

- **否决重排**：匿名 B 对「高达吉士双牛堡」说「不接受」→ 重新推荐后四套方案仍全部试算成功（¥86.50 / ¥33.90 / ¥60.50 / ¥86.50），否决记录随会话保留。
- **多 10 元对比（预算宽松）**：¥120 → ¥130，折中方案没有产生新组合，页面如实显示「方案没有变化」，官方实付仍为 ¥60.50。
- **多 10 元对比（预算收紧）**：¥55 → ¥65，口味方案官方实付从 ¥46.50 变为 ¥60.50，新增麦乐鸡 ×1，页面写明「多花 ¥14.00 换来上面的变化」。增量大于 10 元，是因为跨过加餐门槛，不是直接加价。
- 证据：`outputs/live-verification.json`、`outputs/真实验证-脱敏方案卡.json`、`outputs/browser-verification.json`。

### 关于此前的“两套价格未验证”

上一轮曾有两套方案试算失败，原因是方案里的「蘸酱炸鸡」「牛肉堡单品精选」在官方详情里带必选配置轮次。程序不替用户擅自选配，因此改为**在推荐阶段排除需选配的餐品并重新推荐**，而不是让整张方案失败。本轮四套方案都在此规则下产生。

## 接口（本机）

| 接口 | 作用 |
| --- | --- |
| `GET /api/status` | 连接状态、是否已检测到凭据及其来源 |
| `POST /api/connect` | 重新读取凭据并连接 |
| `POST /api/query` | 按城市 + 公开商圈查门店，返回门店句柄 |
| `POST /api/menu` | 按门店句柄查菜单与优惠，返回菜单句柄 |
| `POST /api/recommend` | 按菜单句柄 + 人数/口味/预算生成四套方案 |
| `POST /api/veto` | `{planHandle, personIndex, itemIndex}`：记录某人不接受某项并重排 |
| `POST /api/upgrade` | `{planHandle}`：同策略预算 +10 的真实对比（同一次会话内缓存） |
| `POST /api/price` | 对某方案重新做官方价格核对 |
| `POST /api/export` | 导出所选方案的脱敏方案卡 |
| `GET /api/evidence` | 工具名 + 状态 + 时间，不含参数 |

浏览器永远拿不到商品编码、菜单原文、价格原文或工具参数；门店、菜单、方案、否决全部由服务端句柄与索引承载。

## 限制与安全边界

- 官方业务场景固定到店自取（`beType: 1`、`orderType: 1`）。
- 不读取收货地址或历史订单；不创建订单、不支付、不自动领券、不兑换积分、不抽奖。
- 只推荐可独立试算的官方单品；套餐、组合、随心选、会员专享、需选配的餐品排除并说明数量。
- 菜单价只用于排序与估算；未完成官方试算一律显示「未验证价格」，菜单价相加不冒充实付。
- 官方价超预算会明确标注。
- 优惠只做有限单券试算，不承诺查询范围外的价格或全局最低价。
- 忌口与「不接受」基于名称/标签匹配，不是配料或过敏原保证。
- 「照顾最难满足的人」只对齐**当前候选**的满足比例，不代表每个人真实满意，也不是全局最优。
- 同机参与，无账号、无实时群聊、无多设备同步。
- 未做现场真人试用记录；`workbuddy.md` 是开发摘要，不是完整对话导出。
